## 2. 审计中已修的 4 个问题

### 2.1 spec 的 `environment.llm` 是字符串，编译后不是合法 RunConfig

E1/E3 spec 写的是 `"llm": "qwen3.8:27b-q4_K_M"`，而 `RunConfig` 要求 `environment.llm` 是对象。编译器把它原样合并进 effective config，导致：

```text
ConfigError: invalid run config: environment.llm must be an object
```

修复：`compiler.normalize_environment()` 把 `llm/embedding/judge` 的短字符串转成 `{"model": ...}`。E1a 的 23 个 plan 现在 23/23 可 build。

### 2.2 切换实现时保留了旧实现的参数

从 R0 的 `meta_schema` 切到 `legacy_flat` 时，`schema.params` 仍带 `fields/evidence/bitemporal/...`，`LegacyFlatExtractor` 只接受 `extract_model`，直接 `TypeError`。同理 resolver 从 `mem0_4action` 切到 `append` 会带 `similarity/threshold/top_k`。

修复：`compiler.set_impl()` 在 `*.impl` 变化时，按目标实现的 `params_allowed` 过滤旧参数；`planner` 例外（planner 的参数由配置层读取，不能清空 analyzer）。E3 从 8/16 失败变为 16/16 可 build；E1a 23/23。

### 2.3 `graph.repr=none` 仍会尝试建图

`ingest.build_store` 无条件 `store.ensure_graph(graph_name)`，而 `graph.repr:none` 没有注册实现，导致 `UnknownImplementation`。

修复：`ingest.py` 在 `graph_name != "none"` 时才建图。E1b 的 graph=none 现在可 build。

### 2.4 `UsePipeline.from_config` 不传配置参数

`UsePipeline.from_config` 的注释说“只传实现声明的参数”，但实际 `resolver_params/answerer_params` 恒为 `{}`，`logic.params`/`answer.params` 被忽略。

修复：按 `params_allowed` 过滤后传入。注意：R0 的 `answer.params`（verifier/max_tokens/...）在 `valid_history` 上本来就不被该实现接受，所以当前 R0 配置仍不会“多出”这些参数；这是实现层的设计，不是本次修完就自动生效。

## 3. 仍然存在的漏洞（按严重度）

### P0-1 · R0 端到端执行器（已解除，需验收）

S6 已提交 `a8c6dfd`：`memlab/experiments/executor.py` + `--executor e2e` + `tests/test_s6_executor.py`。

- `Runtime.load(R0)` 仍抛 `UnimplementedPipeline`，这是**故意 fail-closed**；R0 走显式 `--executor e2e`，不是静默绕过。
- 仍需验收：clean checkout 下 `--executor e2e` 能跑 10 题并写 SQLite；不能把“executor 存在”当成“E1 结果已可信”。

**建议：** 用 `--executor e2e --offline` 跑 2–3 个 E1 候选 × 10 题；再确认 `answer_f1/evidence_recall/tokens/seconds` 写入。

### P0-2 · “声明目录”≠“可运行实现”

`RunConfig` 只用 `configs/variants.json` 的声明目录校验，不检查 registry 是否真的注册。E1b 里有 7 个 plan build 失败：

- `schema.impl = hmem / structmem / amem`：未注册；
- `schema.params.cot`：`MetaSchemaExtractor` 不接受；
- `graph.repr.impl = event_sparse / community`：未注册。

另外这些配置轴实际没被消费：

| 声明轴 | 实际情况 |
|---|---|
| `graph.retrieval.impl` | `retrieve.py` 只读 `graph.retrieval.params`，impl 未使用 |
| `post.dedupe` | `MergePipeline` 没有 dedupe 阶段 |
| `write.consolidator` | W 流水线没有 consolidator |
| `schema.params.cot` | extractor 不接受，也不使用 |

**影响：** 如果直接跑 E1b，会得到 7 个 error run；如果把 `graph.retrieval.impl` 当因子，会得到“无差异”的假结论。

**建议：** 给 compiler/CLI 加 `runnable` 门禁：对每个 plan 做 registry 检查 + 轻量 build；不能 build 的 plan 标记 `runnable=false`，默认不进入正式矩阵，并在报告里列出。补 `tests/test_compiler_contract.py` 的 build 级测试。

### P1-1 · Runner 忽略每个 plan 的 dataset

`Runner.run()` 在 [runner.py](../../memlab/experiments/runner.py#L103) 只调用一次 `load_questions(spec)`；而 E4 的每个 plan 有自己的 `dataset`（数据规模/样本/题数），`Runner` 没有用 plan.dataset。S6 脚本自己按 seed 选题，绕开了这个问题；但 CLI `run --spec e4...` 会跑错数据规模。

**建议：** 按 plan 的 `dataset` 调 `load_questions`；`questions` 显式传入时才覆盖。

### P1-2 · 错误被当成“已完成”，resume 不重试

`ResultStore.completed()` 只要 `(run_id, qid)` 有任何 metric 就返回 True；错误写的是 `metric=error`，所以 resume 会跳过失败题。实测：

```text
first  errors=1
completed after error True
second attempted=0, skipped=1
```

**建议：** 区分 `ok` / `error`；`completed` 只认非 error metric；加 `--retry-errors`。

### P1-3 · 编译器没有去重

`run_id` 带 `index`，两个 effective config 相同但 factor 标签不同的 plan 会拿到不同 run_id；S5 设计里要求去重/随机化，当前没有。

**建议：** 按 `config_hash` 去重（保留一个，记录 aliases），或在矩阵里显式标记 duplicate。
