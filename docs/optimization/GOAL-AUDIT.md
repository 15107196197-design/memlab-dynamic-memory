# GOAL-AUDIT · 总体目标对齐审计

> 用途：检查“代码/测试/实验”时，不只问“有没有 bug”，还要问“这个改动是否服务于项目的总体目标”。  
> 适用：阶段收尾、修复会话、S6–S10 的实验设计评审。  
> 配套：[HANDOFF.md](HANDOFF.md)、[PHASE-CHECKLIST.md](PHASE-CHECKLIST.md)、[SESSION-PROMPTS.md](SESSION-PROMPTS.md)。

---

## 0. 一句话

**这个项目的目标不是“堆更多模块”，而是造一台能做因果归因的实验仪器：同一产品、可配置切换、能回答“哪个能力在什么环境下、对什么指标、值多少成本”。**

所以审计必须同时看三层：

1. **局部正确**：代码能跑、测试通过；
2. **实验有效**：因子真的被 wire、指标真的测到构念、对照真的只差一个因素；
3. **目标对齐**：这个改动是否让“能力 → 实现 → 参数 → 组合 → 环境”的因果地图更清楚。

---

## 1. 项目目标（审计时的“北极星”）

### 1.1 产品目标

- **一个运行时**：B0 legacy、R0 reference、A0–A5 变体都在同一个 `memlab` 包里；
- **六模块**：W 写入 / S 存储 / R 检索 / M 合并 / U 使用 / K 维护；
- **四层插拔**：模块内组件、模块内实现、模块间候选、环境；
- **配置切换**：不允许“每个角度复制一份仓库”；
- **可复现**：manifest、缓存键、seed、dataset/prompt hash、失败样本。

### 1.2 实验目标

| 阶段 | 问题 |
|---|---|
| E0 | B0 基线是否可复现？ |
| E1 | 每个模块内部，哪种实现/参数/模块 LLM 最好？ |
| E2 | 模块之间怎么耦合？检索好是否使用好？是不是 LLM 强？ |
| E3 | 模块组合是否超加/次加？ |
| E4 | 不同 LLM/数据规模/场景下，最优配置是否不同？ |
| E5 | 留出集/第二 Judge/人工确认后，结论是否成立？ |

### 1.3 结论目标

每个结论至少回答：

- **质量**：F1 / Recall / nDCG / Judge；
- **成本**：tokens / 调用次数；
- **延迟**：P50/P95；
- **归因**：系统贡献 vs LLM 贡献；
- **边界**：在哪个 LLM、数据规模、场景下成立；
- **可复现**：commit/config/seed/judge/prompt。

## 2. 审计的 10 个问题

每个 P0/P1 发现都要能回答：

| # | 问题 | 不合格的例子 |
|---|---|---|
| 1 | 这个改动属于哪个模块/轴？ | “优化系统”但说不清 W/S/R/M/U/K |
| 2 | 它是同一个产品里的开关吗？ | 复制仓库/分支做实验 |
| 3 | 这个因子真的被 wire 了吗？ | config 写了 `graph.retrieval.impl`，代码只读 params |
| 4 | 对照是否只差一个因素？ | 同时换 schema + planner + LLM |
| 5 | 指标是否测到构念？ | 用 answer F1 代表“记忆质量” |
| 6 | 有没有把 LLM 能力算成系统能力？ | 不分 L1/L2/L3，直接说“系统提升” |
| 7 | 环境是否进入设计？ | 只在一个 LLM/一个数据规模下给全局最优 |
| 8 | 成本/延迟是否报告？ | 只报质量，不报 tokens/P95 |
| 9 | 能否复现？ | 没有 manifest/seed/judge/prompt hash |
| 10 | 状态是否诚实？ | 未实现/未跑/key 缺失却写成“无差异/已完成” |

## 3. 审计红旗（看到就要标 P0/P1）

- **声明 ≠ 可运行**：`variants.json` 里有，registry 没注册，或 build 时 `TypeError`；
- **配置 ≠ 消费**：config 轴存在，但代码不读，因子是 no-op；
- **静默 fallback**：R0 跑成 B0、cross-encoder 缺失却当已重排、LLM 失败却当答案；
- **mock/offline 冒充真实**：offline extractive F1 写成“LLM 答案质量”；
- **缺 key 却跑 L3**：没有 provider/key，却报告强模型结论；
- **只跑单测，没有端到端**：模块单测过，但 compiler→runner→SQLite 没跑；
- **错误被当 0 分/已完成**：error run 进入均值，或 resume 跳过失败题；
- **只给全局最优**：没有条件策略/环境交互；
- **指标混用**：不同 Judge/不同基准分数直接横比；
- **文档漂移**：HANDOFF 的 commit/测试数/阶段与实际不符。

## 4. 严重度定义

| 级别 | 定义 | 例子 |
|---|---|---|
| **P0** | 让实验结论无效，或产品无法端到端跑 | R0 无执行器；声明未实现变体进入正式矩阵；静默 fallback |
| **P1** | 让归因/比较有偏，或结果不可复现 | 因子 no-op；Runner 用错 dataset；error 当 completed；LLM 混淆 |
| **P2** | 影响效率/可用性/文档，但不直接推翻结论 | 无 dedupe；analysis 太粗；HANDOFF 过期 |

## 5. 审计报告模板

```text
Finding:
- 现象/证据:
- 影响的能力/模块:
- 影响的实验阶段（E0–E5）:
- 严重度: P0/P1/P2
- 是否让某个结论无效:
- 修复建议:
- 验收测试:
```

**每条 P0/P1 都必须写“影响哪个能力/哪个阶段”，不能只写“代码有 bug”。**

---

## 6. 修复会话的额外规则

1. **先对齐目标，再改代码**：读 HANDOFF §2、本文件、审计报告。
2. **不要用“让测试变绿”替代“让实验有效”**：不能 build 的 plan 应标 `runnable=false`，不是删掉测试。
3. **不要静默跳过**：不能跑的变体要列出原因（未注册/参数不支持/缺 key）。
4. **不要扩大范围**：修 P0/P1，不顺手做新模块/新实验。
5. **不要覆盖在途工作**：先看 `git status`/worktree；S6 未提交时用隔离 worktree。
6. **修完必须给 A/B 选择**：本会话继续下一阶段 / 新会话提示词。

---

## 7. 一句话

> **测试通过只证明“代码没坏”；目标对齐才证明“实验有意义”。**
